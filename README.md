# Энергия дня

## 1. Описание проекта

**«Энергия дня»** — небольшое веб-приложение для наблюдения за самочувствием и поиска закономерностей между ежедневными привычками и уровнем энергии.

Пользователь один раз в день оценивает своё состояние по шкале **от 1 до 5**, после чего приложение сохраняет данные и постепенно накапливает историю.

Основная идея:

> Пользователь не должен подробно вести дневник. Достаточно потратить около минуты и поставить несколько субъективных оценок. Через некоторое время приложение помогает увидеть закономерности в собственных данных.

Приложение не ставит медицинских диагнозов и не определяет объективное состояние здоровья. Все основные показатели являются **субъективными оценками пользователя**.

---

# 2. Основные показатели

Каждый дневник содержит следующие показатели по шкале **1–5**:

| Показатель       | Описание                                     |
| ---------------- | -------------------------------------------- |
| **Сон**          | Субъективная оценка качества сна             |
| **Питание**      | Субъективная оценка качества питания за день |
| **Кофе/чай**     | Субъективная оценка употребления кофе и чая  |
| **Алкоголь**     | Субъективная оценка употребления алкоголя    |
| **Активность**   | Общий уровень физической активности          |
| **Настроение**   | Субъективная оценка настроения               |
| **Самочувствие** | Общее субъективное физическое самочувствие   |
| **Стресс**       | Субъективный уровень стресса                 |
| **Энергия**      | Субъективный уровень энергии за день         |

Например:

- `Сон = 4` не означает объективно 4 единицы качества сна;
- `Стресс = 5` означает высокий субъективный уровень стресса;
- `Энергия = 2` означает низкую субъективную оценку энергии.

---

# 3. Энергия является **целевым показателем для аналитики**.

Приложение использует её для поиска взаимосвязей с другими параметрами:

```text
Сон       → Энергия
Питание   → Энергия
Активность → Энергия
Стресс    → Энергия
Настроение → Энергия
```

Например:

> В дни, когда пользователь оценивает свой сон на 4–5, средняя оценка энергии составляет 4.2. В дни с оценкой сна 1–3 — 2.9.

Важно не интерпретировать такую связь как доказанную причинность:

> Не следует говорить «плохой сон вызывает низкую энергию».

Корректная формулировка:

> «В твоих данных низкая оценка сна часто совпадает с низкой оценкой энергии».

# 4. Основной пользовательский сценарий

Пользователь открывает приложение и видит главный экран.

Если дневная запись ещё не заполнена:

```text
Как прошёл твой день?

😴 Сон             4 / 5
🥗 Питание         3 / 5
☕ Кофе / чай      2 / 5
🍷 Алкоголь        1 / 5
🏃 Активность      4 / 5
🙂 Настроение      4 / 5
❤️ Самочувствие    4 / 5
😵 Стресс          2 / 5
⚡ Энергия         4 / 5

              [Сохранить]
```

После сохранения пользователь может:

- посмотреть текущие показатели;
- изменить запись;
- открыть историю;
- посмотреть аналитику;
- получить AI-наблюдения.

Для одного пользователя и одной даты должна существовать **не более одной дневной записи**.

## AI Insights

AI-слой приложения.

Задача:

> Превратить результаты аналитики в понятные пользователю наблюдения и гипотезы.

AI не должен самостоятельно вычислять статистику.

Правильная схема:

```text
Daily Logs
    ↓
Analytics
    ↓
Статистические показатели
    ↓
LLM
    ↓
AI Insights
```

Например, backend вычисляет:

```text
sleep >= 4
average energy = 4.2

sleep < 4
average energy = 2.9
```

LLM получает эти данные и формирует:

> **Сон и энергия**
>
> В дни, когда ты выше оцениваешь свой сон, твоя энергия в среднем тоже выше.
>
> Энергия при сне 4–5: 4.2
> Энергия при сне 1–3: 2.9
>
> Это наблюдение основано на твоих данных за последние 30 дней.

AI не должен придумывать статистические значения.

# 6. AI: техническая архитектура

AI API не должен вызываться непосредственно из React.

Неправильно:

```text
React → LLM API
```

API-ключ окажется на клиенте.

Правильно:

```text
React
  ↓
Node.js API
  ↓
Analytics
  ↓
LLM API
  ↓
Structured JSON
  ↓
React
```

Node.js получает данные пользователя, рассчитывает статистику и передаёт LLM только необходимый контекст.

---

## Формат AI-ответа

LLM должен возвращать структурированные данные, например:

```json
{
  "insights": [
    {
      "type": "sleep",
      "title": "Сон и энергия",
      "description": "В дни с высокой оценкой сна энергия в среднем выше.",
      "confidence": "medium"
    }
  ],
  "experiment": {
    "title": "Понаблюдать за сном",
    "description": "В течение следующей недели обрати внимание, повторится ли эта закономерность."
  }
}
```

Это позволяет frontend независимо от LLM отображать результат.

# 9. Будущее расширение модели данных

На старте используются только субъективные оценки.

Структура должна позволять постепенно добавлять подробные данные.

## Сон

Сейчас:

```text

```

В будущем:

```text
sleep = 1..5
sleep_duration = 7.5
```

Субъективная оценка сна и продолжительность сна являются разными характеристиками.

## Активность

Сейчас:

```text

```

В будущем можно добавить таблицу:

```text

────────────────

```

Например:

```text

Прогулка  45 минут

```

Оценка `activity` при этом сохраняется как субъективная общая оценка активности за день.

Сейчас:

```text

```

В будущем:

```text

────────────────
```

Например:


Субъективная оценка питания и список блюд — разные данные.

# 12. Deployment

Приложение разворачивается на собственном **VPS**.

Используются:

- Docker;
- Docker Compose.

Предполагаемая структура:

```text
VPS
│
└── energy-day/
    │
    ├── docker-compose.yml
    ├── .env
    ├── frontend/
    └── backend/
```

Mинимальный состав:

```text
frontend
backend
postgres
```

PostgreSQL также запускается в Docker.

Данные PostgreSQL хранятся в bind‑mount'е `./data/postgres` (каталог на диске хоста), чтобы база переживала не только пересоздание контейнера, но и `docker compose down -v`. Каталог включён в `.gitignore`; при деплое на VPS его достаточно скопировать с собой как бэкап.

### Первичная инициализация базы

При первом клонировании или изменении схемы БД:

```bash
# 1. Создать первую миграцию (только один раз)
cd backend && npx prisma migrate dev --name init

# 2. Создать Prisma Client
npx prisma generate
```

### Запуск окружений

Проект использует Docker Compose **profiles** для разделения окружений.

#### Dev (разработка с hot‑reload)

Использует `frontend-dev` (Vite на порту **5173**) и `backend-dev` (Node.js + tsx watch на порту **3000**).

```bash
# Полная среда
docker compose --profile dev up -d --build
```

Миграции применяются автоматически при старте `backend-dev` (`prisma migrate deploy` в CMD контейнера).

| Сервис | Адрес | Порт |
|--------|-------|------|
| Frontend | `http://localhost:5173` | 5173 |
| Backend API | `http://localhost:3000/api` | 3000 |
| PostgreSQL | хост:5432 | 5432 |

Для полной очистки:

```bash
docker compose --profile dev down -v --remove-orphans
```

#### Prod (продакшн)

Использует сборанные образы: `frontend` (NGINX на порту **80**) и `backend` (компилированный Node.js).

```bash
docker compose --profile prod up -d --build
```

Сервисы доступны по порту **80**.

Оба окружения используют один и тот же `postgres` и переключаются между собой так:

```bash
# остановить текущее окружение
docker compose down
# запустить dev
docker compose --profile dev up -d --build
# запустить prod
docker compose --profile prod up -d --build
```

Важно: без флага профиля (`--profile dev` / `--profile prod`) команда поднимет только `postgres`, т.к. все остальные сервисы привязаны к своим профилям. Поэтому для запуска приложения флаг обязателен.

### PWA и Push Notifications

Приложение — PWA (mанифест + иконки + service worker c офлайн-кэшем). После входа пользователь получает один раз запрос разрешения на уведомления; при согласии фронтенд создаёт `PushSubscription` через `pushManager.subscribe()` и отправляет её в БД. Каждый день в **20:00 по Москве** бэкенд шлёт напоминание «Незаполненный дневник» пользователям, у которых нет записи за сегодня (одна доставка на устройство в день, дедупликация по `lastReminderSent`).

Особенности:

- **Работает только по HTTPS** (secure context браузера): на VPS обязателен домен + TLS перед nginx. На `http://localhost` всё работает уже сейчас (браузер считает localhost secure context).
- **VAPID-ключи** — статичная EC-пара, генерируется один раз и НЕ истекает. Истекает только служебный JWT на каждый запрос (<24h), но его библиотека `web-push` строит автоматически. Парные ключи хранятся в `.env` (prod) и `.env.development` (dev): `VAPID_PUBLIC_KEY` / `VAPID_PRIVATE_KEY`. Публичный ключ продублирован в `frontend/src/lib/push.ts`.
- **Регенерация пары** нужна только при компрометации приватного ключа: новый набор в `.env` + заменить публичный в `frontend/src/lib/push.ts`; существующие подписки перестанут работать и будут очищены сервером по ошибке 410/Gone.
- Подписки хранятся в таблице `push_subscriptions` и НЕ удаляются при закрытии вкладки — это нужно, чтобы напоминание приходило, когда приложение не открыто. Удаляются только: (1) по событию `pushsubscriptionchange` (пользователь отозвал разрешение / браузер сбросил подписку); (2) по HTTP 410/404 от push-сервиса (недействительный endpoint).
- Cron-джоб выполняется только при `NODE_ENV === 'production'` (в dev напоминание можно запустить вручную вызовом `runDailyReminder()`).
- В nginx задано `Cache-Control: no-cache` для `/service-worker.js` и `/manifest.json`, чтобы клиенты вовремя получали новую версию.

# 15. Backend modules

Backend организуется по функциональным модулям.

## `daily-logs`

Отвечает за:

- создание дневной записи;
- получение записи за дату;
- изменение записи;
- получение истории.

## `analytics`

Отвечает за:

- средние значения;
- статистику по периоду;
- сравнение показателей;
- анализ взаимосвязей;
- поиск лучших/худших дней.

## `ai`

Отвечает за:

- подготовку контекста для LLM;
- вызов LLM API;
- валидацию ответа;
- преобразование ответа в формат API приложения.

## `auth`

Отвечает за:

- регистрацию;
- вход;
- выход;
- проверку пользователя;
- управление сессией.

## `push`

Отвечает за:

- хранение push-подписок (`POST`/`DELETE /api/push-subscriptions`, авторизация обязательна);
- cron-задачу ежедневного напоминания о незаполненном дневнике (20:00 MSK, только production);
- дедупликацию доставки на устройство по дате последнего напоминания;
- очистку недействительных подписок (HTTP 410/404 от push-сервиса).

# 17. Основные архитектурные принципы

1. **Энергия вводится пользователем и не вычисляется приложением.**
2. Все основные показатели — субъективные оценки от 1 до 5.
3. Энергия является целевым показателем для аналитики.
4. Не усложнять модель данных до появления соответствующего функционала.
5. Подробные данные о сне, активности и питании добавлять постепенно.
6. `activities` и `meals` не нужны в MVP.
7. Расчёты и статистика выполняются обычным кодом, а не LLM.
8. LLM используется для интерпретации уже рассчитанных данных.
9. LLM не должен придумывать статистические значения.
10. Не делать медицинских выводов и не утверждать причинно-следственные связи.
11. Frontend не обращается к PostgreSQL напрямую.
12. Все запросы к БД проходят через Node.js backend.
13. API-ключи и другие секреты никогда не попадают во frontend.
14. На первом этапе не выделять отдельный `domain` слой.
15. Не использовать микросервисную архитектуру.
16. Приложение разворачивается на VPS через Docker Compose.
17. PostgreSQL запускается в Docker и использует persistent volume.
18. Новые возможности добавляются постепенно, без преждевременного усложнения архитектуры.

# 19. Цель MVP

Первый релиз должен решать одну задачу:

> **Помочь пользователю понять, какие особенности его дня связаны с его уровнем энергии и самочувствием.**

Минимальный набор экранов:

```text
┌───────────────────────────┐
│      Энергия дня          │
├───────────────────────────┤
│                           │
│  Сегодня                  │
│  История                  │
│  Аналитика                │
│  AI Insights              │
│                           │
└───────────────────────────┘
```

Основной пользовательский сценарий должен занимать **около одной минуты в день**.

AI на первом этапе можно ограничить блоком:

> **«Что я заметил за последние 7/14/30 дней»**

Главная ценность приложения — не количество вводимых данных и не сложность AI, а постепенное накопление персональной истории и возможность увидеть закономерности, которые сложно заметить самостоятельно.
