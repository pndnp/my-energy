# Agents Description

Репозиторий содержит код проекта "Моя энергия". Прочитай его описание в README.md.
В коде и сообщениях пользователю используй только русский и английский языки.

## Подключение к Context7 (MCP Server)

**ВАЖНО:** Конфиг mcporter (`config/mcporter.json`) лежит в корне репозитория. Запускай mcporter из корня проекта. Если команды запускаются из поддиректорий, используй: `mcporter --config ./config/mcporter.json` (от корня) или полную команду из поддиректории:

```bash
# ИЗ КОРНЯ РЕПО (основной способ):
mcporter list context7 --schema
mcporter call context7.resolve-library-id query="value" libraryName="supabase"
mcporter call context7.query-docs libraryId="/supabase/supabase" query="..."

# ИЗ ПОДДИРЕКТОРИЙ (например frontend/):
cd frontend && mcporter --config $(git rev-parse --show-toplevel)/config/mcporter.json list context7 --schema
```

**Принципы работы с Context7:**

- ВСЕГДА начинай с `resolve-library-id`, если пользователь явно не указал `libraryId`
- Не запрашивай старые или устаревшие методы
- Спрашивай про самую свежую версию

## Правила разработки

**ВАЖНО:** ВСЕГДА используй #context7 MCP Server для чтения актуальной документации по библиотекам. Делай это каждый раз, когда используешь в первый раз язык, библиотеку, фреймворк и т.д.


**ВАЖНО:** Перед выполнением задачи создай todo и показывай пользователю прогресс выполнения.  Пока можешь выполнить все шаги — делай все подряд без остановок и запросов. **Останавливайся и выходи к пользователю** только если что-то сломалось или есть противоречия в инструкциях или требуется явное участие пользователя. В этом случае напиши причину остановки. Если делаешь что-то в фоне (проверки написанного когда), напиши пользователю, чем ты сейчас занят.
Делай не больше трех попыток решения, после чего приходи к пользователю.


**ВАЖНО:** Каждый раз, когда в процессе выполнения задачи ты узнал что-то новое и ценное для разработки проекта, запиши это в этот файл так чтобы другая LLM могла повторить это.

ВСЕГДА проверяй код прежде чем вернуть контроль пользователю. Используй линтеры и тесты.

**ВАЖНО:** Если в процессе решения задачи сталкиваешься с нехваткой информации, остановить и спроси пользователя, не пытайся додумать сам. Также допускаются ситуации, когда ты не можешь решить задачу - не выдумывай несуществующие API и не пиши код "лишь бы написать" - остановись, объясни пользователю, с чем возникли трудности и почему, и запроси инструкций.

При написании кода не используй depricated свойства и типы, уточняй информацию о библиотеке с помощью node_modules или #context7.

## Установка зависимостей в проект
**ВАЖНО:** При установке зависимостей в package.json всегда указывай точные версии библиотек (без `^` или `~`).

### Обновление зависимостей (переустановка)

Когда нужно переустановить зависимости:

```bash
rm -rf node_modules
npm cache clean --force
npm i
npm run build
```

После каждого обновления проверяй package.json — не должно быть `^` или `~`, только точные версии.

### Создание frontend с нуля
Следуй инструкции в INIT.md в корне проекта.

### Добавление компонентов через shadcn/ui

```bash
cd frontend
npx shadcn@4.18.0 add card slider input label separator button --yes
```

**КОГДА ЗАПУСКАЕШЬ SHADCN CLI:**
- CLI создаст папку с именем `@` (пустоту). Это баг.
- Удалите папку `@`: `rm -rf frontend/@/`
- Переместите её содержимое в `frontend/src/`: `cp -R frontend/@/* frontend/src/ && rm -rf frontend/@\`
- После удаления добавьте `@/` в `.gitignore` (чтобы случайно не коммитить)

### PostgreSQL в Docker: сообщение "database ... does not exist"

В логах контейнера `energy_postgres` может появляться повторяющийся `FATAL: database "energy_user" does not exist`. Причина: утилиты psql/pg_isready по умолчанию выводят имя БД из имени пользователя, поэтому `pg_isready -U energy_user` без `-d` пытается подключиться к несуществующей БД с тем же именем. В healthcheck'е docker-compose.yml ОБЯЗАТЕЛЬНО указывай `-d energy_day`, иначе логи будут заспамлены ошибкой каждые 5 секунд (при этом контейнер помечается healthy — pg_isready возвращает rc=0).


### Migrations применяются автоматически при старте backend'а

И prod, и dev контейнеры бэкенда стартуют через `prisma migrate deploy` (CMD в обоих Dockerfile'ах), после чего — приложение. Манифесты зависят на healthcheck postgres'а (`depends_on: service_healthy`), поэтому база гарантированно готова. Для первого запуска окружения достаточно только `docker compose [--profile dev] up -d --build` — руками миграции применять не надо.


### Данные PostgreSQL: bind-mount вместо volume

БД хранится в bind-mount `./data/postgres` (не в именованном volume), чтобы пережить `docker compose down -v`. Каталог `data/` в `.gitignore`. Бэкапы не автоматизированы — ручная страховка это copy каталога `data/`.


### Healthcheck в docker-compose: 127.0.0.1, а не localhost

`wget` внутри `node:*-alpine` контейнера резолвит `localhost` сначала в IPv6 `::1`, из-за чего `http://localhost:3000/api/health` падает с `Connection refused` (Node слушает IPv4). В probe всегда указывай `http://127.0.0.1:...` — иначе сервис будет помечен unhealthy, хотя работает.


### Секреты только из .env, никогда напрямую в compose/коде

`POSTGRES_PASSWORD` в docker-compose.yml задаётся как `${POSTGRES_PASSWORD}` (значения в `.env`). В код и конфиг НЕ писать пароли/ключи хардкодом — при коммите они навсегда остаются в истории git (удаление требует squash/peresборка ветки + `reflog expire --expire=now --all && git gc --prune=now`). Пароль БД изменить без потери данных можно через `ALTER ROLE energy_user WITH PASSWORD '...'`.


### `docker compose up` без профиля поднимет только postgres

Сервисы `backend`/`frontend` (prod) и `backend-dev`/`frontend-dev` скрыты за `profiles: ["prod"]` / `["dev"]`. Команда `docker compose up -d --build` БЕЗ флага профиля запустит один лишь `postgres`, из-за чего localhost «не отвечает», хотя compose не выдаёт ошибку. Запускать ВСЕГДА с явным профилем: `docker compose --profile dev up -d --build` или `docker compose --profile prod up -d --build`. Обе среды делят один контейнер postgres, переключение = `docker compose down` + `up` с нужным профилем; данные при этом живут в bind-mount `./data/postgres`.
